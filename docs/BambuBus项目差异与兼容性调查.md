# BambuBus 项目差异与兼容性调查

调查日期：2026-10-25。本文件记录版本证据、实现差异和后续兼容性分析线索。可复用的帧格式与命令说明见 `BambuBus协议分析.md`。

第 4 节保留本项目**适配前**的调查快照。2026-10-25 已实施的修改、配置迁移与测试结果见 [BMCU-U兼容适配.md](BMCU-U兼容适配.md)，不应再用下面的旧行为表判断当前工作区代码。

当前阶段只生成文档，没有修改固件、执行烧录或验证实机打印。下文的“已确认”指源码/提交记录事实；“待验证”指尚不能据此确定打印机行为或停印原因。

## 2. BMCU-U 的新版兼容证据

### 2.1 可以直接由提交确认的改动

提交 `17190641d446d17c76860f373d4211a8c37b1166`，2026-08-26，说明采用 BMCU-X 的 `01.00.06.87`，并称已在 A1/A1 mini `01.08.01.00` 工作。

该提交在 `src/bambu_bus_ams.cpp` 中只改了 `long_packge_version_version_and_name_AMS08` 的前四个字节：

```text
旧字节：15 08 00 00
新字节：57 06 00 01
```

该差异确认了**版本声明是作者进行新版兼容调整的一项实际措施**。它没有增加 040D/040E 处理器，没有增加签名算法，也没有修改该提交中的 Cxx/Dxx 运动响应。

这并不等于“本项目只改四字节就必定兼容”：参考项目在该提交之前已经拥有本项目缺少的运动状态处理、反馈数据和注册行为。

### 2.2 注册和通信稳定性改动

提交 `98965191228a5a0ae39c221b4c4bdb944e04873a`，2026-08-25：

- 恢复 `have_registered` 注册锁存，确认完成后不再对普通发现重复报名。
- 采用首次 `0C`、后续 `0A` 的发现前缀，确认时检查 17 字节前缀加身份。
- 将本地心跳截止间隔从 1000 ms 改为 2500 ms。
- 移除当时使用的在线检测策略模块。

提交说明指向重复注册、连接稳定性等问题。它可以解释兼容性为何还涉及运行时状态，但不能证明打印机认证因此被解决。

### 2.3 打印准备反馈并非此次版本提交新增

`before_on_use_sniff_7f_rows` 的引入可追溯至 `fbff4e3`（2026-04-22，V10.5）。本次两个 CH32 项目均保留同类 45 行数据和 `09/7F` 处理。

因此应区分：

- 2026-08-26 的兼容提交明确改了版本声明。
- `09/7F` 准备和动态反馈是该版本已包含的旧有能力。
- 这些路径在用户机器的新旧打印机固件中是否出现差异，仍需同条件抓包确认。

## 3. BMCU-Flasher 的固件来源

BMCU-Flasher 是 WCH ISP 烧录工具。本次读取版本的 README 将 Bambu 固件指向 BMCU-C-PJARCZAK；`bmcu_flasher_gui.py` 中 `FW_URL` 也指向同一仓库。Klipper 固件有独立来源。

```text
BMCU-Flasher README / bmcu_flasher_gui.py::FW_URL
    -> jarczakpawel/BMCU-C-PJARCZAK
    -> 用户选择的固件发行版与变体
    -> 板上执行的 BambuBus 实现
```

它也支持烧录本地 bin。因此“通过 Flasher 烧录后可以打印”需要继续确认实际选中的固件和变体，不能归因于 Flasher 在打印中执行了另一套认证协议。

## 4. 已核对的实现差异

### 4.1 协议、版本与注册

| 项目 | BMCU-U | 本项目 bmcu-esp（适配前） | 辅助项目 BMCU-C-PJARCZAK |
|---|---|---|---|
| 串口/帧族 | 1,250,000 bps、8E1，3D 长短头 | 启动实参为 1,228,800 bps、8E1；帧族相同 | 相同基本协议 |
| 长帧请求 flags | 接受 `04` 和 `05` | 仅接受 `05` | 辅助参考，具体版本应按解析入口核对 |
| CRC | 39/66 的 CRC8，1021/913D 的 CRC16 | 相同 | 相同 |
| 版本查询 | 21 字节载荷，`57 06 00 01` | 实际发送来自可配置 `AMS_VERSION`；默认 `90.0.0.0` | 当前数组 `00 00 00 0B`，对应 11.0.0.0 |
| 版本名称 | `AMS08` | 实际 0103 分支使用 `AMS08` | `AMS08` |
| 发现前缀 | 首次 `0C`，后续 `0A` | F00 模板为 `16`，没有同样的阶段切换 | 固定编号构建同样 `0C/0A`；AUTO 构建另用 token/分配流程 |
| 身份匹配 | 比较前缀加 16 字节身份 | 同样进行匹配，但前缀、身份构造规则不同 | 固定编号与 AUTO 分支不同 |
| 注册保持 | 单设备 `have_registered` | 每 AMS 各有 `have_registered[4]` | 有注册保持，并增加 AUTO 逻辑 |
| 多 AMS | 编译固定一个编号，每块板处理本编号 | 一块板管理 `AMS_COUNT × 4` 个通道 | 可编译固定编号或自动分配 |
| 长帧 AMS 地址 | 接受 `0700` | 当前解析路径接受 `0700` | AUTO 注册后还有槽位地址匹配分支 |
| 040D/040E | 未发现对应处理器 | 未发现对应处理器 | 未发现对应处理器 |

定位：U 的 `get_packge_type`、`get_package_online_detect`、`get_package_long_packge_version`；本项目的 `send_for_Fxx`、`refresh_serial_identities`、`send_for_long_packge_version`、`src/settings_storage.h`；辅助项目相应处理器及 `BMCU_AMS_AUTO` 分支。

本项目实际设备中保存的 `AMS_VERSION` 可能已被用户修改，源码默认值不代表当前板子正在发送的值。调查实机时应同时读取设置和实际 `0103` 回复。

`VERSION_NAME` 宏、未使用的 AMS Lite 模板以及模板注释不能代替实际分支判断。本项目 `0103` 的实际输出在发送前会被设置值覆盖。

### 4.2 打印中的状态转换与反馈

| 路径/字段 | BMCU-U | 本项目（适配前） | 对后续调查的意义 |
|---|---|---|---|
| `09/7F` 使用前准备 | 明确进入 before_on_use | `is_before_on_use` 只识别 `09/A5`，`09/7F` 落入一般 09 分支 | 已确认存在实质行为差异，优先对照失败日志 |
| `09/A5` 准备反馈 | 从 send_out 转入时 pressure 可为 4700，否则 2B00 | before_on_use 统一 2B00 | 同一状态名不保证相同输出 |
| Cxx `09/7F` 动态响应 | 45 行数据，响应次数推进 | 无该表、无对应回放 | 不能只迁移一个状态判断而漏看反馈 |
| 准备后早期 on_use | 有 1E34 的计数处理 | 常规 2B00 | 需要连续多帧比较，单帧不足 |
| 送出转使用的等待 | 参考内部上限 15 秒 | 内部等待 5 秒 | 都是设备实现值，不是已确定的打印机硬性时限 |
| `07/00` 在送出中 | 显式包含 send_out 停止路径 | 仅从 on_use / before_on_use 转 stop_on_use | 可能影响暂停、准备失败或取消时的停料行为 |
| `FF/03/00` 回抽 | 当前状态为退料准备/使用/使用准备/暂停时可进入回抽 | 只在 before_pull_back 后进入回抽 | 应用同一日志核对实际到达状态 |
| `FF/01` | 不无条件清空当前使用状态 | 若 loaded 有效则置 idle 并清除全局选择 | 属于打印中/状态轮询值得重点验证的差异 |
| 无当前通道反馈 | pressure FF74、meters 0；Cxx 相邻字 0008 | pressure FFFF、meters -1.0 | 空闲默认值不同，不能盲目视为等价 |
| 普通未知区 | CH32 模板包含 F8/F7 等原始值 | C_test 为另一组固定模板 | 需要原始字节对照，未知不等于无关 |
| Dxx 请求通道回显 F[12] | 回显请求中的 F[9] | 固定 FF | 与运动反馈中的当前通道字段不同，不能合并解释 |
| 堵转组合 | 本地堵转路径写 F06F，相邻字 1CE7 | 协议反馈函数没有该组合 | 与物理异常上报有关，不能混作认证错误 |
| 长度来源 | 运动测量更新累计米数 | 支持测量，协议状态机另有有限虚拟计米 | 需同时核对运动、计米和打印机反馈 |

定位：U 的 `set_motion`、`get_package_motion`、`get_package_stu_motion`、`src/Motion_control.cpp`；本项目 `process_motion_state_machine`、`get_pressure_value`、`set_motion_response`、`C_test`。

上表提供具体排查点，不证明所有差异都是缺陷，也不证明其中某一项已导致用户描述的停印。主要参考是单固定 AMS，直接照搬其全局变量还可能破坏本项目现有的多 AMS 隔离。

## 5. 参考实现中不能直接当作协议规范的部分

### 5.1 Cxx 特殊回放的字节重叠

紧凑结构体给出的基础布局：

```text
F[29]     filament_stu_flag
F[30..33] last1
F[34..37] last2
```

但 `get_package_motion` 的特殊回放实际执行：

```text
将 row.last1 的 4 字节写到 out + 29
将 row.last2 的 4 字节写到 out + 33
```

结果为：F[29] 的普通位图被覆盖，两个原始块实际占 F[29..36]，F[37] 仍保留模板字节。两个 CH32 项目都存在这种处理。

已确认的是**实际写入偏移与结构体字段偏移不同**。尚不能断言应整体右移一字节修正，也不能断言这是厂商真实字段布局：它可能是为了匹配观察数据，也可能包含历史实现问题。迁移前需要原始抓包确认；直接按成员名解释特殊响应会得出错误结论。

首行例子：`last1=F3F4FA57`、`last2=B4B5F0F7`，实际 F[29..36] 是 `57 FA F4 F3 F7 F0 B5 B4`，F[37] 为基础模板剩下的 `B1`。

### 5.2 心跳快速路径没有整帧 CRC16 验证

U 的实际 ISR 经 `_bus_port_deal::irq` 接收。识别到 `C5/20` 后丢弃剩余字节，到达声明长度后刷新心跳截止时间，没有对完整心跳调用 `package_check_crc16`。

这是一种实现取舍，不能写成“BambuBus 心跳无需 CRC16”。本项目当前集中校验有效心跳的方式不应因参考实现有快速路径而被放宽。

同文件中的一些 valid/heartbeat 注释还可能比实际校验条件宽泛，报告以执行分支为准。

### 5.3 本地超时不等于打印机超时

U 的 `bambubus_heartbeat_seen_fast` 使用 2500 ms，但函数注释仍有 1000 ms 的旧说明。本项目将有效总线报文与有效心跳分别计时，其中心跳超时是 5000 ms。

这些数值控制模拟设备自己的在线判断。没有打印机内部代码或失败前后抓包，不能据此断定打印机会在 1 秒、2.5 秒或 5 秒断开 AMS。

### 5.4 50 μs 位于启动发送之前

U 的 `bambubus_run` 构造回复后有 `delay_us(50)`，随后返回主循环，由 `send_package` 启动 DMA。注释“确保回复发送完成”与实际调用顺序不符。

正确解释是：这是构帧后、实际开始发送前的一段软件等待。发送完成仍由 UART TC 控制。不能据此认定总线回复总耗时固定 50 μs。

### 5.5 活跃接收链路与残留文件

U 仓库有 `printer_rx_framer.cpp/.h`，但本次搜索调用位置后，实际 UART ISR 走的是 `_bus_port_deal::irq`。报告没有把未接入的独立 framer 当成运行中的接收队列实现。

U 的普通接收只有一个已发布待消费帧槽，另一个缓冲用于正在接收的帧；待消费槽占用时新完成帧可能丢弃。本项目已有两槽完成帧队列和发送反压处理。移植协议差异时应保留这些已经存在的保护，而不是整体替换收发框架。

### 5.6 不能由 ACK 推定落盘完成

U 的耗材写入处理后会设置保存标记，保存由主循环其他逻辑执行；本项目也有自己的静默检测、限频和回读校验流程。ACK 的线上格式与 Flash 写入是否完成属于不同问题。

## 6. 兼容说明中的不同结果

本节只复述对应固定源码版本附带的兼容说明，不是本次实机认证，也不是官方最新固件清单。

| 来源 | 明确写出的观察/说法 | 本次可接受的解释 |
|---|---|---|
| U README | A1/A1 mini 在 01.08.01.00 测试工作 | 有具体版本依据，但没有随附的完整测试日志 |
| U README | P1/X1/P2/H2D 的较宽泛兼容描述 | 未给出足以逐一核对的打印机固件版本，不能泛化为所有新版 |
| PJARCZAK README | A1/A1 mini 01.05.00.00–01.07.02.00 可工作，可能有 HMS 提示 | 属于带提示可用，与无提示/认证成功不同 |
| PJARCZAK README | A1/A1 mini >=01.08.00.00 的错误可能阻断切片项目，建议其 OrcaStudio 处理错误和重试 | 涉及桌面发送工作流；不能据此认为 AMS 固件新增了认证实现 |
| PJARCZAK README | 部分 P1/X1 新固件首次打印可进行，后续需重新连接或重启 | 开始一次打印不等于可连续执行多个任务 |
| PJARCZAK README | 部分较新 P2S/H2D/X2D 等固件停在 Preparing AMS | 手动进退料正常不等于打印准备能通过 |

用户提到的“新版在打印中通信失败就停印”需要保留为待定位现象。现有说明涉及打印前准备、任务间认证、切片软件报错、运动反馈等不同阶段，不能在没有日志时合并成“持续打印认证失败”一个原因。

本次没有找到三套已查协议源码中可成功响应 `040D/040E` 的实现。附带说明对这两个命令的描述可以作为抓包线索，但不能替代证书/挑战的原始帧和成功过程证据。

## 7. 后续抓包最应关注的路径

| 时点 | 需要对照的帧/状态 | 要回答的问题 |
|---|---|---|
| 开机枚举 | 05、0103、0402、021A | 注册前缀、身份、版本是否稳定匹配 |
| 第一次进料后 | Cxx/Dxx 的 09/7F 与 09/A5 | 新旧打印机是否选择了不同准备路径 |
| 准备进入打印 | Cxx 的未知区及 pressure 多帧序列 | 是否需要连续变化，是否在固定反馈处失败 |
| 稳定打印 | 07/7F、0x20、实际米数、响应间隔 | 是丢帧、延迟、数据不合理，还是出现额外命令 |
| 暂停/取消 | 07/00 与当前实际电机状态 | 打印机是否已经要求停止，本地是否响应 |
| 换色 | 09/3F、FF/03/00、新通道送出 | 是否在通道切换和历史状态上出现不一致 |
| 本地异常 | F06F/1CE7 与传感器状态 | 是设备主动报堵转，还是通信/身份错误 |
| 第一任务结束、第二任务开始 | 注册、版本、040D/040E、Preparing AMS 状态 | 失败是否属于任务间重新检查 |

对同一设备优先同时保存打印机错误码、任务阶段与完整双向帧。只有带错误码的截图片段或只记录已识别命令的摘要，不能排除未知字段变化。

上述线索已用于本次适配；代码与回归测试见独立适配说明。实机停印原因仍需双向日志确认，不能把软件测试通过写成已验证的打印机兼容结论。
