## 2026-11-04 恢复默认配置

“设置 → 设备操作 → 恢复默认配置”调用 `POST /api/settings/reset`，由 `handle_config_reset()` 处理。接线和 AMS 数量恢复平台默认项目，通道参数、AMS 身份、日志开关和更新设置恢复固件默认值；保留 WiFi 凭据及 mDNS 名称。该操作复用 `settings_reset_to_defaults()` 生成快照，恢复当前运行配置后通过 `settings_save_snapshot()` 写入并回读校验，成功才重启。设备忙碌返回 409，保存或回读校验失败返回 500，失败不重启且保留当前运行配置。回读失败无法保证 Flash 仍是原记录，需要重试。

原“恢复出厂设置”及 `POST /api/factory` 保留，仍清除 WiFi。网页确认框说明重置范围，请求期间防止重复提交，取消不发送请求，失败显示原因并允许重试。

`test_project_presets.py` 使用真实恢复接口和存储函数，检查完整默认快照、重启加载、WiFi 清除调用隔离、忙碌拒绝、写入失败及回读失败。`test_web_config.cjs` 检查按钮及确认文案、取消、重复提交、成功、409/500、断线后重试和手机布局；可通过 `WEB_TEST_DEVICE_SCREENSHOT` 保存设备操作区截图。本机 GCC 和 Edge 网页回归通过，截图已检查，`pio run -e esp32c3` 编译通过；未编译其他平台、烧录或验证实机重启后重连 WiFi。

## 2026-11-04 退料时间检测

通道卡片的“退料超时（秒）”旁提供问号说明，输入框右侧的“检测时间”复用 `/api/motor`，以 `dir=-1`、`duration=29999` 发起退料。按钮变为“停止”，设备返回的剩余时间配合浏览器时钟显示实际退料用时，排队不计时；点击停止调用原停止接口，确认停车后向上取整回填并自动保存。正常达到上限时保存为 30 秒，不足 3 秒不修改原设置。未修改后端接口或时长范围。

测时只保存在当前页面；切换页签重绘卡片仍保留本次检测，整页刷新会丢失测时记录，已提交的电机动作仍受 29999 毫秒上限约束。断开设备连接时保留停止入口，不保存不确定的结果。前端计时受状态采样和网络延迟影响，不能精确分辨两次轮询之间的停车原因；主机测试和页面截图不代替实机退料验证。

## 电机目标与排队回归

`python -B tools/tests/test_bambu_bus.py --motor-control` 编译真实 `BambuBus.cpp`、`BMCU.cpp` 的电机队列、命令执行、定时器、主循环和 `handle_manual_motor()`，只替换硬件输出、采样与 HTTP 传输。原有六组场景如下，另有上文的时长与总微动两组场景：

- `printer_target`：Cxx/Dxx、跨 AMS 通道、打印机接管手动和微动辅助动作；同向保持输出，反向切换，重复退料不续期，新进料可打断定时退料。
- `motor_queue`：打印机与手动共用 FIFO，同通道重复请求不重复入队，排队方向可更新；并发受限时等待，实际启动后才计算时长。
- `queue_updates`：打印机接管同通道排队目标；准备完成、停止、换通道或进料前缺料时取消失效任务。
- `manual_requests`：网页回调不驱动电机，主循环执行停止和取消排队；停止只取消当下，后续打印机请求可以重新启动。
- `manual_bus_timeout`：总线超时取消打印机排队，保留本地手动运行及队列。
- `motor_guards`：无电机引脚、扩展器离线、无效通道及点动时长仍拒绝启动。

网页 `test_web_config.cjs` 检查打印机/手动排队来源、方向、位置、取消后手动重启和手机布局。以上是主机和模拟接口验证，不代表实机进退料、电气换向或连续打印验证。

## 运行

已有 GCC/Clang 时：

```powershell
python tools/tests/test_bambu_bus.py
python tools/tests/test_bambu_bus.py --settings
```

可通过 `CXX` 指定编译器，或使用 Zig。Windows 禁止运行新生成的 EXE 时，可用 Zig 0.15.2 或更新版本编译到 WASI，再由 Node.js 执行：

```powershell
python tools/tests/test_bambu_bus.py --zig C:/path/to/zig.exe --wasi
python tools/tests/test_bambu_bus.py --zig C:/path/to/zig.exe --wasi --settings
```

移除 `--wasi` 即运行本机测试。临时产物位于系统临时目录。WASI 不开放文件目录，执行 19 组协议/电机测试，明确跳过仅本机支持的 `queue_threads`。设置套件执行 9 组测试。

`bambu_u_motion_golden.h` 保存从固定 BMCU-U 源码数据构造的 45 个完整期望帧，CRC 用独立逐位算法生成。它不读取本项目生产表计算期望值，能检查整帧偏移、序号及未知区；这些样例不是本次硬件抓包。

设置存储 9 组场景：

- `current_custom`：当前格式四份身份和参数逐字节保留，90.0.0.0 不被自动改写，自动末位按 AMS 编号、自定义末位原样保留、数量增减后身份稳定，启动不重复写入。

- `bad_crc`：当前魔数但 CRC 错误的记录恢复默认并回读校验。
- `empty`：空片生成当前格式默认记录。
- `write_failure`：写入失败可恢复内存快照，存储仍保留原记录，重试后正常加载。
- `readback_failure`：回读损坏必须报失败，可恢复内存快照并重新保存。
- `default_write_failure`：默认记录写入失败，下次启动重试，成功后不再重复写入。

## AS5600 启动栈溢出回归

`python tools/tests/test_as5600.py --zig C:/path/to/zig.exe` 提取真实模拟采样代码，使用 Zig 0.15.2 或更新版本及 Node.js WASI 验证同毫秒返回零、100 毫秒上限、时钟回绕、重新初始化可复现，以及 10 万次采样的有限值、均值、方差和距离范围。

Espressif32 8.0.0 / RISC-V GCC 14.2.0 环境下，旧 `std::normal_distribution` 经 `generate_canonical` 调用了 `logl`。故障合宙 C3 固件的 PC `0x420f8478`、RA `0x420f847c` 均位于 `logl`，反汇编在 `0x420f847a` 显示调用自身，导致 `loopTask` 约 8 KB 栈耗尽。地址仅对应当次故障 ELF。

修复采用单精度极坐标正态采样，保留种子、标准差和距离限幅；重新初始化时也清除采样缓存。验证目标固件不再包含 `logl` 符号，再检查设备启动和持续运行，不能仅凭主机数值测试判定目标数学库正常。

2026-10-28 合宙 C3 验证：10 万次主机采样测试通过；实际编译、COM3 烧录及写入校验通过；新 ELF 无 `logl` 符号，设备启动后能连接 WiFi 并持续响应状态接口。随后 TLS 日志确认 OTA 另有内存分配失败，缩减 C3 日志缓冲释放 80 KB 后，设备可用堆约 95 KB，GitHub Pages 清单检查成功。没有执行线上旧固件的下载安装，也没有验证连续打印。
